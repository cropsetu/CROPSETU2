Headline: Railway, one replica of each service, roughly $110 per month all-in. At this size the architecture you already have is comfortably over-provisioned. Two things still matter and neither is a scaling problem: the database has no tested restore, and a handful of correctness defects bite identically at 100 users and at 100,000.

1. Executive summary

Recommendation

Railway. One replica of each of the four services. Do not plan a migration. At 10,000 registered users the system peaks at roughly 10–30 requests per second, which is around 5–10% of what a single Express replica handles. There is no capacity problem to solve, and no cost pressure that would justify moving.

The work worth doing is therefore not scaling work. It is (a) giving the database a restore path, (b) closing correctness defects that do not care how many users you have, and (c) a $90/month media-delivery fix that currently costs more than every server you run combined.

The headroom this buys

backend/src/config/db.js pins connection_limit=12 per replica, and the comment there derives it by Little's law for a 300 RPS target:

fast path   300 req/s × ~4 queries/req = 1200 q/s × ~2 ms       ≈  2.4 busy connections
slow tail   1% at ~250 ms (geo scans, trigram, admin aggregates) ≈  3.0 busy connections
            fleet ≈ 5.4 busy;  ×2 so queueing stays negligible   ≈ 11 fleet-wide

Your peak is 10–30 RPS, one tenth of that. The same pool that was sized for four replicas at full load is now serving a single replica at a tenth of the load. Concretely:

  • One Express replica is enough, with roughly 5–10× headroom before the event loop becomes the constraint.
  • Database connections: 12 of 100. The budget in the baseline reserved 72 for Express across six replicas; you will use twelve. A connection pooler is not merely unnecessary, it would be solving nothing.
  • 300–500 concurrent sockets on one Node process is unremarkable. Node handles thousands. Socket.IO's Redis adapter exists to coordinate multiple replicas; with one replica it is inert, and it already falls back to the in-memory adapter cleanly (server.js:93).
  • Twelve cron schedules on one replica run twelve times, not twelve times N. The leader-lock multiplication problem needs two or more replicas to exist at all.

3. Platform choice

The shape of the stack, not its size, is what narrows the field. Four properties of the code disqualify most platforms before price is considered.

There is no exit trigger at this scale

The 100,000-user version of this document set a threshold for leaving Railway at roughly $400/month. At 10,000 users the bill lands near $70 and stays there. You will not approach that threshold. Treat the platform question as closed and stop spending attention on it — that is the correct outcome of asking it.

4. The one thing that does not get easier: the database

Highest-severity finding, and it is not a scaling issue

The Railway PostgreSQL plugin is a single container attached to a single volume: no point-in-time recovery, no automatic failover, no read replica, and no restore you have ever exercised.

This database holds orders, payments, the AI credit ledger, KYC records and consent history. A volume failure, a mistaken manual SQL statement, or an accidental service deletion is unrecoverable. Ten thousand real users' orders are not less valuable than a hundred thousand.

Three facts already recorded in the repository make the exposure worse:

  1. Schema changes are applied by hand. prisma/migrations/ contains 13 directories but only 65 CREATE TABLE for 90 models and 23 CREATE TYPE for 43 enums. It cannot rebuild a fresh database, so prisma migrate deploy is unavailable and changes go through prisma/manual/*.sql. Manual SQL against production with no PITR is the most common way small teams lose data.
  2. Two tables are invisible to Prisma. ai_scan_diagnoses and ai_scan_feedback are created by FastAPI through asyncpg and do not appear in schema.prisma. A restore rebuilt from the Prisma schema silently omits them.
  3. There is no CI. No .github/workflows runs the backend tests, the FastAPI tests, or Prisma validation on any push. With hand-applied migrations, CI is the only guard rail there could be.

5. What does not scale down

Reducing the user target removes capacity work. It removes none of the following, because none of these are load-dependent. Several are more dangerous at small scale, where there is not enough traffic for a problem to announce itself.

DefectReferenceWhy 10,000 users does not help
No Celery worker liveness signalPERF-010 FastAPI reports healthy while zero workers are deployed, and every crop scan queues forever. At 100 scans a day this goes unnoticed for longer than it would at 1,000 — there is no traffic spike to make it obvious. Users simply stop getting results.
AI spend cap missed chat and voicePERF-038 The daily cap was only ever measuring scans. A runaway loop or a prompt-injection costs the same whether you have ten users or ten thousand — the cap is protection against a bug, not against volume.
Credit and spend reservation racesPERF-040, §53 A read-then-write check lets concurrent requests all pass the same limit. It needs two simultaneous requests, not two thousand. One user double-tapping a button is enough.
Payment and stock concurrency§51, §52 Overselling one item to two buyers is the same defect and the same refund at any scale. The serializable transaction and the unique constraints must hold from the first order.
Unbounded process mapsPERF-039 A long-lived Map keyed by request or IP grows with unique keys seen, not with concurrent users, and a single replica that never restarts accumulates them indefinitely. Small scale makes this worse, not better.
38 failing tests, no CIPERF-001, §60 Roughly 24 of the 38 are one contract disagreement: tests assert HTTP 422 where middleware/validate.js sends 400. Until that is settled there is no clean regression signal for any change, including the database migration in §4.
Dev OTP fallback in productionMSG91 / DLT With no MSG91 key the server returns the OTP in the API response instead of sending it. That is a complete authentication bypass if it ever reaches production, and it is entirely independent of user count.

The reframe

Scaling the target from 100,000 to 10,000 users deletes most of the performance backlog. It deletes none of this table. If there is one section of this document to act on, it is this one — the platform question above was already answered by the status quo.

Two consolidations available, and why to skip one

  • Drop the standalone Node worker. The Express replica already runs an in-process BullMQ consumer at QUEUE_CONCURRENCY=5, so the separate worker.js service is optional. Saves $7/month. Keep it anyway — it is the only isolation between a slow notification job and the HTTP event loop, and $7 is not a reason to give that up. Verify that only one of the two is consuming the queue in production, so jobs are not picked up by both.
  • Reduce FastAPI to one uvicorn worker. WEB_CONCURRENCY defaults to 2. At this traffic one is genuinely sufficient and it halves the FastAPI memory footprint and its asyncpg pool usage. Saves ~$3/month and some database connections. Low risk, do it if you are tuning.

Growth headroom

The useful question is not what 10,000 users costs, but at what point the bill changes shape:

7. Region and latency

Railway's nearest region is Singapore; there is no India region. The users are farmers on low-end Android devices on 2G, 3G and weak LTE. Both facts are fixed, and the gap between them is closed by a CDN rather than by a migration.

PathRTTCold connection setupCost to obtain
India → Singapore, direct55–75 ms~200–225 mscurrent state
India → Cloudflare India PoP10–25 ms~40–75 msfree, one hour
India → Mumbai origin15–30 ms~55–90 msfull platform migration

Cold setup approximated as three round trips for TCP plus TLS 1.3. Real figures vary widely on rural mobile networks.

The middle row is the one to buy. Proxying through Cloudflare terminates TLS at an India point of presence, so the phone's expensive handshake happens locally and the Singapore leg rides a warm, pooled connection. It recovers most of the penalty for nothing, and it leaves the origin exactly where it is.

The residual 40 ms between Cloudflare and a Mumbai origin is not worth a migration. The baseline records GET /agristore/cart issuing 13 database queries and POST /agristore/orders/confirm issuing 25–35. Against a 500 ms p95 target, application and query time dominate by an order of magnitude. Fix the cart before fixing the continent.

Enabling it, in order

  1. Proxy the API domain through Cloudflare (orange cloud). Free plan.
  2. Confirm WebSockets are enabled in the dashboard. If they are not, Socket.IO silently degrades to HTTP long-polling, which multiplies your request count and defeats the point of having sockets at all.
  3. Do not cache /api/v1/* by default. Authenticated JSON must never be shared between users. Add cache rules only for genuinely public, non-personalised reads.
  4. Check proxy-aware rate limiting before you switch it on. Rate limits key on client IP; behind a proxy every request arrives from a Cloudflare address unless trust proxy is set and the forwarded header is read. Get this wrong and the limiter either buckets the whole country together or trusts a spoofable header.
  5. Serve media through the CDN, not the origin — see §8.

8. Media: the line item larger than your servers

At 10,000 users, image delivery costs more than every server you run

Modelled at ~$99/month on Cloudinary against ~$67/month for the entire backend, database and cache combined. The identical traffic on Cloudflare R2 or Bunny is $2–11/month.

2,000 DAU  ×  ~30 image views per active day  ×  ~80 KB per card-sized transform
  =  4.8 GB / day
  =  ~144 GB / month of delivery          (Cloudinary's free allowance ≈ 25 GB)
Provider144 GB deliveryStorageNotes
Cloudinary (current)$99included Free tier is exceeded around 25 GB, which lands somewhere near 2,000 daily actives. The next tier is a step, not a slope — you pay $99 the month you cross it.
Cloudflare R2 cheapest$0~$1 Zero egress through Cloudflare is the entire reason to pick it. Generate sizes on upload with sharp in the Node worker you already run.
Bunny.net~$1.50~$1 Plus roughly $10/month for the image optimiser if you want on-the-fly transforms rather than writing them. Simplest drop-in.

Saving: about $88 per month, or $1,050 a year, for roughly a day of work — and it grows with every user you add. This is the highest return per hour available anywhere in this document.

Why it is tractable

  • The database stores publicId and URL, never binary. Changing delivery host is a URL-construction change, not a schema migration.
  • backend/src/config/cloudinary.js centralises upload handling behind one module, with limits already set per surface: 15 MB general, 5 MB avatar, 100 MB video.
  • The upload path has been worked on recently — PERF-025 (uploads cut off while Cloudinary was still receiving) and PERF-035 (a process buffering unbounded 100 MB videos) are both recorded — so it is understood code, not archaeology.

Order of operations

  1. Move delivery first, keep Cloudinary for transformation if you want the smallest possible first step. Most of the saving is in egress.
  2. Generate four sizes on upload (thumbnail, card, detail, original) in the Node worker. Fixed cost at write time beats metered transforms at read time.
  3. Audit the mobile list screens for a 3000 px original rendered into a 120 px card. Do this before migrating, or you will simply pay for the same mistake more cheaply.
  4. Signed direct upload — the client requests a signed URL, uploads straight to object storage, and posts back only a media ID. This also removes the base64-through-JSON path that the AI scan currently uses, cutting Node memory and GC pressure in the same change.

Week 1 — before real users

5Confirm the dev OTP fallback cannot fire in production30 minAuthentication bypass. One environment variable stands between you and it.

Week 2 to 3 — correctness

  1. Settle the 400-vs-422 contract and get the test suite green. Roughly 24 of the 38 failures are that one disagreement. Until it is fixed nothing else has a regression signal.
  2. Add CI that runs the backend suite with --runInBand, the FastAPI tests, and prisma validate. Parallel jest is not a usable signal — the suites share one database and deadlock.
  3. Extend the AI spend cap to chat and voice, and make every reservation atomic.
  4. Bound the fallback maps — max size or TTL, so a single long-lived replica cannot leak.
  5. Verify payment and stock concurrency holds under two simultaneous requests. Two, not two thousand.

Week 4 — cost and polish

  1. Migrate media delivery to R2 or Bunny. ~$88/month, roughly a day.
  2. Audit mobile list screens for oversized images before or alongside that migration.
  3. Pin AI model routing to the cheap tier by default and confirm the cap is enforced.
  4. Load test at 50 and 100 concurrent — well above your real peak — and record RPS, p95, p99, database connections and queue depth. This is a one-afternoon sanity check, not the staged campaign a 100,000-user target would need. Mock the AI providers so the test does not spend real money.

After that, stop

There is no phase two of hosting work at 10,000 users. The next infrastructure decision is a second Express replica somewhere around 25,000 registered users, and it is a dashboard setting. Point the engineering effort at the product instead — that is what the headroom in §2 is for.

11. What this document does not know

  • No production telemetry exists. Every cost and load figure is modelled from resource shapes read in the code, not observed. The first real bill will correct them.
  • The 20% daily-active ratio is inherited, not measured. 10,000 registered is confirmed; the 2,000 DAU that follows is an assumption carried from the project directive. Real engagement could be half or double that, which moves peak RPS between ~5 and ~60 — all of it inside one replica, so the recommendation is insensitive to being wrong here.
  • Engagement drives the media model. Thirty image views per active day is an assumption. At ten, Cloudinary's free tier might still hold; at a hundred, the media saving is three times larger than stated.
  • Provider prices and regions change. Confirm Railway's current rates, Neon's Singapore availability, and Cloudinary's current free allowance before acting on a specific number.
  • The 38 failing tests mean there is no clean regression signal today, which makes every item in §10 riskier than it needs to be. That is why they are in week two.
One-line summary. Stay on Railway with one replica of each service — roughly $110/month all-in, and the platform question is closed. Spend the saved effort on a database you can restore, the correctness defects in §5, and moving image delivery off Cloudinary.
