01What this changes

The repository already carried a 12,190-line ARCHITECTURE.md with a scaling analysis and a 54-item defect register. This audit does not restate it — it tests it.

Eleven auditors read one subsystem each; each dimension then went to a verifier instructed to refute its findings and to default to refuted when evidence could not be reproduced. That pass killed eleven claims and corrected roughly forty-five more, mostly arithmetic that had been overstated and line citations that had drifted.

Three conclusions differ materially from the prior document:

RT-01

The presence broadcast is not a scoping problem. It is dead weight.

The prior prescribed scoping io.emit('user_online') to relationship rooms. No client subscribes to it at all — the only occurrence of user_online outside the backend is a doc comment. The fix is deletion, not a room design: no client contract change, no subscription bookkeeping, and the accompanying users write per connect goes with it.

backend/src/socket/chat.socket.js:83, :263  ·  shared/services/socket.js:18 (comment only)
P0ConfirmedHand-verified
CRIT-01

One line caps every AI request at 30 seconds, four layers below the code that budgets for 300

httpServer.timeout = 30_000 was added to stop Slowloris. Express waits 120 s for /ai/chat, 55 s for voice and up to 300 s for a synchronous scan; the mobile clients were deliberately raised to 125 s and 200 s, with comments explaining that a shorter timeout "aborts slow-but-successful replies mid-pipeline (and the user still gets charged)". The socket is destroyed at 30 s regardless. This is the manufactured trigger behind the orphaned-credit retries that were attributed to user behaviour.

backend/src/server.js:57  ·  frontend/src/services/aiApi.js:166
P0Critic findingHand-verified
AI-03

The app uploads five full-resolution images per scan and the pipeline throws four away

The client encodes up to five images to base64 at full quality — deliberately, per its own comment — into a single JSON body, which is why a 50 MB parser exists. FastAPI validates images[:1] and the Celery task materialises "the FIRST valid image (single-image pipeline — the multi-image feature was removed)". Up to 80% of the largest request body in the system is encoded, transmitted, parsed and discarded.

frontend/src/services/aiApi.js:139-160  ·  fastapi/routes/scan.py:72  ·  fastapi/jobs/tasks.py:74-76
P0ConfirmedHand-verified
Why this one matters most. AI-03 makes the headline P0.5 recommendation — migrate scans to direct signed uploads — substantially less urgent. Sending one image instead of five is a client-side change of two lines that removes ~80% of the payload today, with no signing endpoint, no ownership table and no backward-compatibility window. The critic also notes the signed-upload migration would move bytes onto the Cloudinary bill to pay for images the pipeline discards, and would remove the point at which credits are debited before bytes land.

02Execution order

Ranked by what makes other work measurable, not by severity. This order differs from the prior document's, which opened with PgBouncer.

  1. Pin DB_CONNECTION_LIMIT to an explicit number

    connection_limit derives from os.cpus().length * 2 + 1, and Node's os.cpus() reads the host's CPU count, not the container's cgroup quota. On a shared 32-core Railway host a single replica claims 65 connections against an assumed max_connections of 100.

    Not the biggest problem — the reason it is first is that every other tier's arithmetic is computed against this denominator, and the denominator is currently unknown. DB-01, DB-09

  2. Break the auth → 401 → refresh → logout chain

    A Prisma failure inside authenticate() returns 401 ("fail closed — never admit a request we couldn't validate"). The shared client turns any 401 into a refresh-and-replay costing five more statements, and cold-start session restore deletes the refresh token on any network error. A DB stall therefore converts into a self-amplifying stampede and then into permanent mass logout recoverable only by SMS re-auth.

    Separate transport failure from auth failure: return 503 when the lookup itself failed. AUTH-02, CRIT-07, MOB-01

  3. Raise httpServer.timeout above the AI budget

    Restores the latency envelope every other layer was already written for, and stops manufacturing the double-charged retries. CRIT-01

  4. Fix the Socket.IO Redis adapter before touching the chat poll

    The adapter's client pair is built with retryStrategy: () => null — it never reconnects, while the main client and BullMQ both do. One blip permanently kills cross-instance delivery until redeploy.

    The ordering trap: the unconditional 10 s chat poll is the only thing currently masking this. Delete the poll first and wire waste becomes silent message loss. OPS-01, RT-06, CRIT-06

  5. Make degradation visible

    logger.warn only emits when isDev. 123 of 163 warn sites are fail-open degradation notices, so in production every Redis fallback, leader-lock miss, queue-inline execution and cache failure is silent. Nothing below this line can be measured until it is fixed.

    OPS-02 — backend/src/utils/logger.js:84-86

  6. Send one image per scan

    Two lines in the client. Removes up to 80% of the system's largest request body immediately. Then re-evaluate whether signed uploads are still worth their complexity. AI-03, AI-01, AI-02

  7. Delete the presence broadcast; fix the mandi upsert; cache the auth read

    Three independent, well-understood changes with no ordering constraint between them. RT-01, A2-06, AUTH-01

DB-05

Celery reuses one module-level asyncpg pool across per-task asyncio.run event loops

A pool created on one event loop and reused on another holds connections bound to a closed loop. Under load this surfaces as connection errors that look like Postgres problems and are not.

The image CMD is timeout 60 npx prisma db push --skip-generate; node src/server.js. 05Complexity report

The reporting format the brief requires, for the changes where complexity is the argument.

Socket presence broadcast

RT-01 · backend/src/socket/chat.socket.js:83, :263
Current
io.emit('user_online') on connect, io.emit('user_offline') on disconnect, each preceded by a users UPDATE.
Time
O(C) per event, C = all connected sockets fleet-wide, amplified by the Redis adapter publishing to every node → O(0)
Space
O(1) event state → unchanged
Problem
At 3,000 concurrent sockets, every connect and disconnect writes 3,000 frames plus one row update. No client has ever listened.
Proposal
Delete both emits and the paired isOnline write. Re-introduce scoped rooms only when a screen actually needs presence.
CPU
Removes the fleet's only O(C)-per-event path and one Postgres write per connection.
Risk
None identified — no subscriber exists. Verified by grep across all four clients.
Tests
Socket integration test asserting no broadcast on connect; existing connectionLimiter tests unaffected.

Authentication hot path

AUTH-01 · backend/src/middleware/auth.js:51-68
Current
Per authenticated request, serially: HS256 verify → Redis GET on the jti denylist → SELECT tokenVersion, isActive FROM users WHERE id=$1. No cache.
Time
Q = a·R user SELECTs/sec (240/s at R=300, a=0.8), each O(log n) on the PK → <25/s at a 15 s TTL with >90% hit rate
Space
0 bytes retained → bounded ~256 B/entry, hard ceiling ~13 MB at maxSize 50,000; ~1 MB at realistic concurrency
Problem
Honest finding: at the stated scale this is not a throughput bottleneck — 240 qps of a PK probe is under 2% pool occupancy. What it actually does is double the statement count of every cheap read, add 1–2.5 ms of serial latency to 100% of traffic, and make Postgres a hard availability dependency of authentication itself.
Proposal
BoundedMap({maxSize: 50_000, ttlMs: 15_000}) — the primitive already exists at backend/src/utils/boundedMap.js with LRU + lazy TTL, currently used at only 2 of ~16 sites that want it. Leave the denylist GET uncached so single-device logout stays instant. Invalidate cross-instance by cloning the existing Redis pub/sub pattern from featureFlag.service.js:116-152.
Staleness
1–3 ms with pub/sub healthy; 15 s worst case with Redis down, against an access-token TTL of 900 s that already exists by design — 1.7% of the current window.
Risk
Makes the eight scattered tokenVersion write sites a correctness requirement rather than a stylistic nit. Enumerate them before shipping.
Tests
Hit/miss/expiry unit tests; an integration test asserting a tokenVersion bump invalidates within the window.

Mandi price persistence

A2-06 + DSA-03 · backend/src/services/mandiPrice.service.js:148-166
Current
R sequential awaited upserts against a never-matching where, each therefore an INSERT, fire-and-forget after the response is sent.
Time
O(R) round trips, R up to 5,000 per sync → O(R/1000) batched statements
Space
Table grows without bound at R rows per sync, duplicating the same (commodity, market, priceDate) forever → bounded by distinct business keys × retention window
Proposal
Ordered, and the order matters: (1) dedup existing rows in SQL, keeping the freshest per key; (2) add @@unique([commodity, market, priceDate]) — this will fail while duplicates exist; (3) replace the loop with createMany({skipDuplicates}) plus a targeted update; (4) use the expiresAt column that is already written; (5) revisit partitioning only once the deduped table justifies it.
DB
Removes R×5 index entries per sync on the fastest-growing table. Read paths keep the same five indexes.
Risk
Step 2 against a live duplicated table fails hard. It must follow step 1, and the boot-time db push (DB-06) will retry it on every replica start.
Tests
Upsert idempotency test; a dedup migration test over a fixture with known duplicates.

10Where this leaves the architecture

The modular monolith is the right shape. Nothing found here argues for microservices, Kafka, sharding or a search cluster.

Three additions are justified by evidence, and only three. Everything else on the list is a change to code that already exists.

The three additions

PgBouncer in transaction mode — but only after DB-06, because boot-time db push takes a session advisory lock that transaction pooling cannot hold. Set statement_cache_size=0 on the asyncpg side. Interactive $transaction and Serializable retries were checked and do not break under transaction pooling.

A dedicated scheduler replica — 12 node-cron schedules currently run on every latency-serving web instance; 10 are leader-locked, 2 deliberately are not and therefore multiply by replica count. Gate the register behind CRON_ENABLED. None of them is given a timezone, so all fire at container-local time.

Observability before capacity — queue depth, oldest queued job, Celery worker heartbeat and circuit-breaker state are not exposed anywhere. A FastAPI service reports healthy while every scan sits queued forever if no worker is deployed. This is what makes the rest measurable, and it starts with logger.warn.

11Method and limits

Eleven read-only auditors, one per subsystem, each followed by a verifier told to refute, plus a completeness critic that enumerated all 37 backend routers, all 23 admin routers and all 6 FastAPI routers against the merged findings. 25 agents, ~1,470 tool calls, 3.1M tokens. Of 146 findings, 134 went through the adversarial pass and 15 died there — a 11% refutation rate, and every one of those is work not done.
